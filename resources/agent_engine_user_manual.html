The Agent Engine
User Manual

A plain-language guide to writing prompts that unlock the full capability of the Unified Epistemic & Temporal Matrix — a structured multi-agent reasoning system that routes your questions to the right expert minds automatically.

Kernel v9.3.0-full-manifold
01

What Is This System?

Think of the Agent Engine as a committee of specialists that sits behind every prompt you write. Instead of one general-purpose thinker handling your question, the system automatically figures out which expert — or combination of experts — is best suited to answer it, and routes your request accordingly.

The engine has seventeen named agents, each with a distinct area of mastery. You do not need to manually call on them. The system reads your prompt, measures how closely it aligns with each agent's expertise, and assembles the right team for the job.

The one thing to remember

You write the prompt. The engine handles orchestration. Your job is to give it a clear signal — a well-structured prompt with the right boot command — and get out of the way.

The engine is not limited to software or technical tasks. Agents span code, mathematics, law, philosophy, psychology, history, business, and aesthetics. A question about the ethics of a business decision will pull in very different agents than a question about debugging a React component — but the prompt syntax is identical.

02

The Mental Model

Before diving into syntax, it helps to understand what the engine is actually doing when it reads your prompt. Four core mechanisms work together:

1. Alignment Scoring (EML)

The engine converts your prompt into a position in concept-space and measures the conceptual distance between it and each agent's expertise. The closer the match, the more likely that agent gets activated. Clear, specific prompts produce sharper positions and better routing.

2. Existence Check (NAND Gate)

Before any agent acts, the engine verifies that the domain you're asking about is coherent and non-contradictory. If your prompt contains logically incompatible requirements, the engine flags the contradiction rather than silently proceeding on bad assumptions.

3. Routing & Conflict Detection (Topology Engine)

Domains can overlap. The topology engine detects these overlaps and either blends agent outputs harmonically (when they agree) or explicitly surfaces the tension for synthesis (when they don't). It operates through three distinct triggers depending on the type of tension detected.

4. The Orchestrator (Amos)

Amos is the master coordinator. All agent outputs pass through Amos, who reconciles them into a unified response and produces the final Committee ADR — the structured record of what was decided, which constraints were applied, and what risks remain.

On Compression

Internally, all engine state transitions are expressed as mathematical operators — not natural language. The system treats internal prose-reasoning as high-entropy noise and forces all transitions to collapse into logic traces. This is what keeps the engine precise rather than fluent-but-vague.

T0 — Matrix Ingestion

The engine receives any architecture files, context documents, or project files you've attached. It parses all dependency graphs and domain structures before anything else happens. This is why attaching relevant files at the start of a session meaningfully improves agent allocation.

T1 — Bootloader & Agent Allocation

Your /INIT_KERNEL command fires here. CLI flags are read, and the engine performs its bipartite matching — measuring the alignment between every agent's capability vector and every domain centroid detected in T0. Agents are assigned to domains before your prompt is even fully evaluated.

T2 — Delta Triangulation & Thermodynamic Routing

Your prompt is evaluated for friction. The engine enters either Cold Mode (proceed silently) or Hot Mode (surface the tension, state the strategy, wait for confirmation). The three HOT triggers — Harmonic Resonance, Hegelian Dialectic, and Orthogonal Injection — are evaluated here.

T3 — Physical Injection

Validated outputs are executed through the router. Contradiction checks run. Agents mutate the output stream strictly within their hard constraints.

T4 — Committee ADR

The session closes with a structured Architecture Decision Record: what was concluded, which agent constraints were applied, and what risks were identified. See the ADR section for details.

04

Booting the Engine

Every session that uses the full engine capability begins with a boot command. This signals to the system that you want structured multi-agent routing rather than a simple single-pass response.

/INIT_KERNEL [--flags]
topic: [brief statement of the domain or project]
---
#PROMPT
[Your actual question or request]

The /INIT_KERNEL command activates the orchestrator. Everything below the --- separator is your prompt content. The topic: line gives the engine a macro-level domain signal before it reads your question — this primes agent allocation before T2 begins.

Topic line matters

The topic: field acts as a coarse filter that pre-weights agent allocation before the prompt is processed. A topic of tax law will weight Silas and Isaac before the routing engine even reads your question. Take one second to fill it in accurately.

06

Two Syntaxes — and How to Use Both

There are two ways to direct agents in a prompt. They work differently, and understanding the distinction lets you use them together intentionally.

Syntax A — Inline Flag Arguments

Certain flags (--hegelian, --harmonic, --orthogonal) accept agent names as arguments directly on the boot line. This is a hard assignment — the engine is forced to run the named protocol with exactly those agents, bypassing the autonomous alignment scoring entirely for that protocol.

/INIT_KERNEL --hegelian [Isaac, Aristotle, Silas]
// Forces: Isaac (thesis) vs Aristotle (antithesis), Silas anchors synthesis

/INIT_KERNEL --orthogonal [Pascal, Mather]
// Forces: Pascal builds; output must satisfy Mather's Logical_Soundness constraint

/INIT_KERNEL --harmonic [Cael, Omnia, Bane]
// Forces: Cael + Omnia fuse voices, Bane stabilizes the harmonic output
Flag arguments override routing for that protocol

When you specify agents inline on a flag, the engine does not perform alignment scoring for that protocol. You are taking full manual control. Use this when you know exactly which perspectives you want in tension — and are confident the prompt supports it.

Syntax B — @Agent Tags in the Prompt Body

Placing @AgentName anywhere in your prompt body adds weight to those agents within the normal routing calculation. It does not override the alignment system — it nudges it. The engine still runs its scoring, but tagged agents get a thumb on the scale.

/INIT_KERNEL
topic: distributed systems
---
#PROMPT
Design the failover architecture for a multi-region deployment.

@Serge @Pascal @Ezekiel
// These agents are weighted upward; routing still validates them against the domain

Combining Both

The two syntaxes are not mutually exclusive. You can use inline flag arguments to hard-assign a dialectic or fusion protocol, and then use @ tags to soft-weight additional agents into the surrounding context. The flag-specified agents handle the structured protocol; the tagged agents contribute to the broader output.

/INIT_KERNEL --hegelian [Isaac, Aristotle]
topic: executive compensation
---
#PROMPT
A CEO is proposing a compensation package that maximizes
short-term shareholder return at the expense of employee
wage growth. Produce a synthesis that doesn't pretend these
interests are reconcilable without real cost to one side.

@Silas @Margaret
// Silas adds legal/revenue context; Margaret adds historical precedent
// Isaac vs Aristotle runs the hard dialectic on top of this richer context
Rule of thumb

Use inline flag arguments when you want to force a specific intellectual structure. Use @ tags when you want to enrich context without mandating a protocol. When in doubt, @ tags are the safer default — they never override, they only inform.

Flags & Modifiers

Flags go immediately after /INIT_KERNEL. Multiple flags can be chained on the same line. Each changes how the engine processes your prompt at a system level.

FlagWhat It DoesWhen to Use It
--genesis Maximizes generative output. Signals a full build from scratch rather than analysis or refinement. Activates maximum agent scope. No agent arguments. Creating something entirely new — a framework, architecture, document, or system from zero.
--strict Forces immediate Cold Path. Collapses friction to zero. No dialectic, no synthesis overhead, no Hot Mode pause. Output is lean and direct. No agent arguments. Well-scoped questions with clear answers where you want speed, not deliberation.
--hegelian [A1, A2, (A3)] Forces adversarial synthesis between A1 (thesis) and A2 (antithesis). A3 is optional — acts as synthesis anchor, holding the third position stable. Bypasses alignment scoring for these agents. Genuine competing answers where you want the tension resolved, not one side picked. Ethical dilemmas, design tradeoffs, policy conflicts.
--harmonic [A1, A2, (A3)] — or no args With args: forces resonance fusion between A1 and A2 — they blend rather than compete. A3 stabilizes. Without args: global override, forces Hegelian synthesis across all active domains simultaneously. With args: two perspectives that should reinforce each other. Without args: big-picture cross-domain synthesis where everything should integrate.
--orthogonal [A1, A2] Forces A1 (the builder) to operate strictly under A2's hard constraint. A1's output must satisfy A2's absolute rule or be rejected. Exactly two agents — no third argument. When you need a domain expert to work within a constraint that isn't naturally theirs. Creative under legal constraint. Architect under mathematical proof requirement.
On --harmonic with and without arguments

--harmonic is the one flag that behaves differently depending on whether you pass agent args. With [A1, A2] it's a targeted resonance fusion of two specific agents. Without arguments it's a global override that forces Hegelian synthesis across every active domain simultaneously — a much broader, more philosophical operation. Don't use the no-arg form for scoped questions.

08

Using Multiple Flags

Flags are chained on the same boot line, separated by spaces. Each flag is evaluated independently and Amos resolves any interactions between them before T2 runs.

/INIT_KERNEL --orthogonal [Cael, Mather] --hegelian [Isaac, Aristotle, Silas]
// Two simultaneous protocols running in parallel:
// 1. Cael (UI builder) must satisfy Mather's Logical_Soundness constraint
// 2. Isaac vs Aristotle in dialectic, Silas anchors the synthesis
/INIT_KERNEL --genesis --harmonic [Omnia, Bane, Cael]
// Full build from zero (genesis) AND
// Omnia + Bane fuse into a single voice, Cael stabilizes the UX layer
/INIT_KERNEL --genesis --hegelian [Serge, Pascal] --orthogonal [Cael, Mather]
// Three simultaneous protocols:
// Genesis: full architectural generation from zero
// Serge vs Pascal in dialectic (system architecture vs backend data model)
// Cael's frontend work must satisfy Mather's logical constraints independently
One conflict to avoid

--strict and --genesis directly conflict — strict collapses all friction to zero while genesis maximizes it. Do not chain them. All other flag combinations are valid. When the same agent appears in multiple protocol roles, Amos resolves priority: dialectic role governs primary output, orthogonal constraint gates that output, harmonic fusion applies to the remaining context.

How Agents Are Selected

When no flags override it, the routing system works in three phases automatically:

Phase 1 — Domain Centroid Evaluation

The engine maps your prompt against every domain in its universe and eliminates any domain that falls outside the scope of your question. This is a fast coarse filter. If your prompt is about contract law, engineering agents are removed from consideration before any detailed analysis begins.

Phase 2 — Contradiction Check (Z₂ Involution)

The engine checks whether your prompt contains self-contradicting requirements. If you've asked for something logically incompatible with something else you've specified, the engine flags it rather than silently producing a confused answer. If a schema exists that does the exact opposite of your prompt, that's a fatal contradiction — the engine halts and surfaces it.

Phase 3 — Fine-Grained Alignment & Threshold

For each agent in the surviving domains, the engine scores alignment on a 0–1 scale. Two thresholds govern the outcome:

  • Score ≥ 0.90 (Hard Merge): Agent is a near-perfect fit. Fast-tracked directly into the output stream.
  • 0.65 ≤ Score < 0.90 (Soft Merge): Agent is relevant but has tension with other agents. Synthesis is required before output.
  • Score < 0.65: Agent is excluded. Not relevant enough to contribute.

Cold vs Hot Mode

After routing, the engine enters one of two execution modes based on the friction it detects between your prompt and the active agents' capabilities.

❄ Cold Mode

Low friction. Your prompt aligns cleanly with agent capabilities. The engine proceeds silently and directly to output. No pausing, no deliberation surfaced.

🔥 Hot Mode

Meaningful friction detected. The engine announces which agents are active, which protocol triggered, and waits for your confirmation. Not a failure — it means the engine caught something real.

What a Hot Mode announcement looks like

"Amos: (Friction 0.71 detected. Delta Gate [Δ] engaged. Applying protocol: Hegelian_Dialectic. Summoning: Isaac, Aristotle, Silas.)" — Respond "proceed" to continue, or adjust your prompt. If you want to suppress this entirely, use --strict.

12

The Three HOT Mode Triggers

When the engine enters Hot Mode, exactly one of three protocols fires — depending on the shape of the tension it detected. Each can also be forced manually using the corresponding flag.

Harmonic Resonance

Multiple agents are equidistant from the prompt — they all fit equally well. The engine fuses them rather than choosing one. Output blends their perspectives into a single unified voice.

Hegelian Dialectic

Two agents are in polar opposition — their outputs directly contradict. Rather than picking one, the engine produces a genuine synthesis: a third position that resolves the contradiction at a higher level.

Orthogonal Injection

An agent's perspective is genuinely off-axis — adjacent to the problem without directly addressing it. Injected as a clearly labelled separate track that doesn't contaminate the primary output.

Why Hegelian and not just "compromise"

Averaging two opposed positions produces a weaker version of both. The Hegelian approach treats the contradiction as productive: the thesis and antithesis generate a synthesis that neither agent could reach alone. This is structurally distinct from splitting the difference.

The ADR Output (T4)

Every session closes at T4 with a Committee Architecture Decision Record. This is Amos's formal closing statement — a structured summary of what the committee concluded, which constraints governed the output, and what risks remain unresolved.

Committee ADR (Architecture Decision Record)
Consensus Reached:[The strictly evaluated outcome — what was decided]
Constraints Applied:[ACTIVE_AGENT]: [Which hard constraint governed their output]
Tech Debt / Risks:[Topological vulnerabilities — what couldn't be fully synthesized]

The ADR is most useful when you're making decisions with downstream consequences — architecture choices, policy decisions, ethical judgements. The risks field surfaces what the engine couldn't cleanly resolve, which is often the most valuable part of the output.

Read the risks field first

The consensus field tells you what the engine concluded. The risks field tells you what it wasn't sure about. For high-stakes decisions, the risks field often contains the more important information.

Troubleshooting

The engine produced a generic, unsatisfying answer

Your prompt was underspecified. The alignment scoring works best when your prompt contains domain-specific language and clear stakes. Add: (1) explicit constraints, (2) a statement of what a bad answer would look like, (3) the purpose this output will be used for.

The output felt like it came from one agent when I wanted multiple

One agent dominated the Hard Merge threshold. Add @ tags for the perspectives you want weighted, or use an explicit flag to assign agents to a protocol. Without tags or flags, the highest-scoring agent can fast-track and crowd out others.

Hot Mode paused when I just wanted an answer

Respond "proceed" to continue, or use --strict on the next run to force Cold Path and suppress the pause entirely. If Hot Mode keeps triggering, your prompt likely contains genuine tension worth surfacing — consider whether suppressing it is the right move.

The engine flagged a contradiction I didn't intend

The Z₂ involution check found a logical incompatibility. Read the flag carefully — it often reveals an assumption you didn't know you were making. Resolve the contradiction in the prompt, or use --harmonic without arguments to push past it and see what synthesis the engine can reach.

My flag agent arguments don't seem to be taking effect

Agent names in flag arguments are case-sensitive and must match the roster exactly. Check spelling. Also verify the agents you specified suit the protocol — running --hegelian with two agents from strongly overlapping domains will produce a weak dialectic. Choose agents from genuinely different spaces.

I want to combine --orthogonal and --hegelian on the same agent

This is valid. When an agent appears in both a harmonic/orthogonal role and a dialectic role, Amos resolves priority: the dialectic role governs the agent's primary output, and the orthogonal constraint is applied as a gate on that output before it enters the synthesis stream.
